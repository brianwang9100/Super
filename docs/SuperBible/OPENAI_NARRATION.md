# Optional OpenAI narration

Status: implemented on `codex/openai-narration`; awaiting manual listening validation before PR work.

## User setup

Settings → Narration presents two connection cards in the model-list style: **Apple enhanced voices** and **OpenAI**. Each card shows a blue **Set up** action until configured, then muted **Configured** text; tapping the card opens its setup or management modal. Apple's status comes from installed Enhanced/Premium voices and is refreshed when returning from Settings. Its modal explains the Read & Speak (or Spoken Content) → Voices download steps and links into iOS Settings. OpenAI's modal accepts a narration-only API key and explains billing and data sharing. A top-right checkmark Save action, matching the note editor’s glass and haptic treatment, connects the chosen key, enables OpenAI narration, and returns to the connection list; there is no enable toggle in this modal. Save stays disabled until a new or existing credential is selected. Reopening a saved narration-only key shows synthetic bullets, just like model registration; focusing clears the placeholder for replacement, and leaving it untouched preserves the Keychain entry. The form never reads the saved secret into its field. The saved-key caption and preview, stop-preview, and remove-key buttons are omitted. A red **Clear downloaded narration** action opens a native confirmation explaining that playback stops, downloaded audio is removed, and regenerating it may incur API charges; Cancel leaves the downloads intact. A saved but disabled OpenAI connection remains configured, with a subtitle stating that narration is turned off. Settings → Models → OpenAI also offers **Use OpenAI voices for narration**, defaulting on in a new setup draft. Saving the draft confirms that choice; canceling does nothing. Existing installs remain unconfigured until the user saves. An explicitly saved off preference remains off when another model is added.

The user selects one narration credential. Adding another Chat model preserves that selection unless **Use this key for narration** is chosen. The active Chat model has no effect on the narration provider. Only credentials explicitly identified as OpenAI and using its canonical HTTPS endpoint qualify; protocol-compatible custom servers are not OpenAI credentials. Legacy model rows gain an explicit provider identity when their setup is saved.

The voice chooser uses a native popover up to 360 points wide, with fixed OpenAI-then-Apple sections and accessible company labels. Marin is the first OpenAI default, followed by Cedar and the remaining built-in voices. The selected control shows the voice name and company on separate lines; menu rows also include the company. Apple remains available without a key. OpenAI failures offer Retry or **Use Apple voice**, without silently switching billing sources.

While audio is preparing, the shared play/pause button displays an activity indicator without changing the player's height. It remains tappable to pause and exposes “Preparing audio” as its accessibility value. The same control handles initial preparation for Apple and OpenAI; downloaded verses hand off without entering a loading state. A slow look-ahead request reports buffering before waiting for the download, and playback clears that state when the next clip starts.

Saving never requests speech. Play in the narration player starts generation. The setup modal explains AI-generated audio and API billing; the player keeps its company label without repeating that disclosure. A ChatGPT subscription does not include API usage.

## Implementation

- Core owns `SpeechGenerating`, the fixed OpenAI speech request, `ProviderAudioSetup` (a company-neutral composition contribution), and main-actor `AudioActivity` for microphone arbitration.
- Bible owns the narration settings record and GRDB repository, Keychain-backed setup controller, provider-neutral voice identity, cloud playback service, native audio player, and audio cache.
- Chat persists optional `providerId` metadata and commits the audio setup contribution only after model/key saving succeeds. Credential changes are published through the event bus.
- SuperBible's composition root connects Chat's safe credential references to Bible's setup; neither applet imports the other. SuperOS continues to use Apple narration.
- The speech request uses `gpt-4o-mini-tts-2025-12-15`, MP3, generation speed 1, and calm verbatim-reading instructions. Playback speed is applied locally. HTTPS redirects are refused.
- Authentication failures are classified from the provider's structured reason: only an explicit `invalid_api_key` becomes an invalid-key message. Missing scopes or insufficient permissions explain audio/project access; an unrecognized 401 remains a general authorization failure. Logs contain only the HTTP status and a closed set of local failure names, never provider messages, response bodies, or credentials.
- Verse text is split at word boundaries under a conservative 1,600 UTF-8-byte limit, preserving the input text. Highlighting follows audible playback events. Only one following verse's first clip is prefetched.
- Stop, navigation, provider changes, and microphone capture invalidate pending playback generations. Late responses cannot start playback. Pause while downloading waits before starting the player.
- Preferences live in Bible's single `narrationSettings` row with revision checks. Raw keys live only in Keychain, using the same `AppleKeychainClient` as model registration and `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`. Narration-only keys are owned by Narration settings and retired when replaced; borrowed Chat keys are never deleted by narration cleanup.
- Generated audio lives in a backup-excluded, disposable SQLite BLOB cache under Caches, bounded to 100 MiB of audio with least-recently-used eviction. The key includes exact text, model, instructions, format, and voice. This uses one atomic database entry instead of a file plus a metadata record. If disk cache initialization fails, playback uses an in-memory cache.
- Playback remains foreground-only. No microphone recording or live voice conversation is added by this feature.

### Queue design

Keep the provider-neutral verse queue: Apple synthesizes queued utterances locally, while OpenAI generates and caches verse clips with one-verse look-ahead. This preserves verse highlighting, skip/restart controls, selected passages, and bounded speculative API usage. Whole-chapter audio would need a separate way to map playback positions to verses and seek within the recording. If listening tests still reveal gaps on short verses, evaluate a bounded buffer of upcoming clips while retaining the same queue and transport interface.

## Validation before a PR

Automated checks cover request fields, safe errors, input limits, company identity, opt-in and opt-out persistence, key ownership, explicit credential selection, stale drafts, cache eviction, Unicode segmentation, late-response cancellation, pause during buffering, microphone preemption, and Chat's two-step setup commit. Schema snapshots include both additive migrations. The connection list, Apple download modal, OpenAI setup modal, and narration player have light, dark, and XXL snapshots. The latest changes pass 318 Core tests, 726 Bible tests, and 61 affected iOS snapshot cases locally, covering connections, setup, the voice chooser, and transport layouts. The authentication regression first reproduced permission-related and unrecognized 401 responses being mislabeled as invalid keys; it passes with reason-based classification. The Keychain rejection regression asserts that a failed secure write leaves no enabled connection or credential reference. Transport snapshots intentionally remove the repeated billing footer, put buffering inside the center button, and cover permission and general authorization errors. Buffering tests cover cached handoffs, waiting on unfinished look-ahead, pausing that wait, and returning to audible playback within a segmented verse. Cache-clearing coverage verifies that playback stops and downloaded audio is deleted while the narration credential and enabled connection remain intact. The native ProgressView has no app-specific Reduce Motion branch; the snapshot harness cannot override SwiftUI’s read-only Reduce Motion environment. An injected installed-voice probe verifies that Apple’s connection status updates after a download; the narration picker rescans when returning to the app or closing connection settings.

Manual validation uses the dedicated `SB-1a93-OpenAI` iPhone 17 simulator on iOS 26.4.1 (`23E254a`) with Xcode 26.4.1 (`17E202`). Build the interactive app with `CODE_SIGNING_ALLOWED=YES CODE_SIGN_IDENTITY=-`: unsigned simulator builds cannot save Keychain entries. A separate `SB-1a93-Narration-QA` simulator reproduced the unsigned failure and verified that signing allows a disposable test credential to save, marks OpenAI Configured, and reveals all 13 voices. Enter a real API key in the simulator, then check:

1. Open Apple’s **Set up** modal, check the download instructions and Settings link, then return. On a device with downloaded Enhanced/Premium voices, confirm **Configured** and the updated narration voice menu.
2. Open OpenAI’s **Set up** modal and save the narration-only key. Confirm its card changes to **Configured**, then play Marin from the narration player and listen for pronunciation, naturalness, clipping, and startup latency.
3. Open a chapter's Narrate action. Confirm OpenAI is above Apple and both the menu and selected control clearly identify the company.
4. Try pause/resume, 0.75×–2× speeds, next/previous verse, and switching company while speaking.
5. Stop during preparation, navigate to another chapter, and background the app. Audio must not restart afterward.
6. Choose Apple in the voice picker and confirm Apple remains usable without OpenAI requests. Open OpenAI settings and tap **Clear downloaded narration**. Cancel once to verify downloads remain; confirm on a disposable cache to verify playback stops and downloads are cleared while the connection remains configured.
7. Try an invalid key / airplane mode and verify the recovery message and explicit Apple fallback. Replay cached audio offline.
8. Add an OpenAI Chat model, then a second one. Confirm the draft toggle defaults correctly and the original narration key remains selected unless explicitly replaced.

No real user API key was used in automated testing. The isolated UI smoke test used a disposable invalid credential and verified the expected rejection without billable generation. Subjective audio quality, production key permissions/billing, Bluetooth routes, and physical-device interruptions remain manual checks. The simulator is the review checkpoint; do not open or merge a PR until the user finishes validation.

An authorized diagnostic preview on September 6 used the QA simulator's existing narration-only credential through the normal app flow. OpenAI returned HTTP 401 with the explicit `invalid_api_key` code. The credential was not read out, replaced, or copied to the review simulator. This confirms the response for that saved entry, not whether it matches a working key used elsewhere. The signed build was installed in both narration simulators while preserving their data.

API reference: [OpenAI text-to-speech guide](https://developers.openai.com/api/docs/guides/text-to-speech).

Apple setup instructions follow the [iOS Read & Speak guide](https://support.apple.com/guide/iphone/hear-whats-on-the-screen-or-typed-iph96b214f0/ios) and [enhanced voice download guidance](https://support.apple.com/en-us/111798). Deep linking is best-effort; the modal also gives the full navigation path if iOS opens Settings at another location. The dedicated iOS simulator opens the Settings home screen and exposes a reduced Spoken Content pane without voice downloads, so installing Enhanced/Premium voices requires physical-device validation.

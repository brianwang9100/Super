## 1. What this is

Three classes of short AI-generated study notes, surfaced as tappable bubble glyphs in the Bible reader and book picker:

- **Book-level**: author intro, summary, historical context — shown beside the book name in the picker (cards display in that canonical category order).
- **Chapter-level**: summary (and optional outline) — shown beside the chapter title in the reader.
- **Verse-level**: historical context, clarification, cross-references — shown after the last verse of a contiguous range the user selected.

All annotations are generated by the user on demand via the user's current Chat LLM (AFM on-device by default; BYOK Claude / Gemini / Ollama / etc. if the user has upgraded). The app ships **no pre-generated content** — every row in the database was produced by an LLM call the user explicitly triggered. SuperBible takes no editorial position on theological accuracy.

## 2. Concepts & terminology

| Term | Meaning |
|---|---|
| **Annotation** | One row in the `bibleAnnotation` table. Represents one *card* — a single titled note attached to a target. A book / chapter / verse range can have many annotation rows; each renders as a separate card in the popover. |
| **Target** | What the annotation is attached to: `.book`, `.chapter`, or `.verse`. |
| **Category** | The semantic role of a card — `.author`, `.summary`, `.historical`, `.clarification`, or `.reference`. Stored as an `Int` (1…5) whose value *is* the canonical display order. It is the single source of truth for both ordering and rendering: `.reference` renders as a tappable citation button, every other category as markdown prose. |
| **Source** | Where the annotation came from: `.user` (the user tapped to generate this one) or `.userBulk` (the bulk runner — future, M-B / M-C). Same write path, different tag. |
| **Bubble** | The on-screen glyph indicating an annotation exists (filled) or invites generation (empty). |

## 3. Data model

Single GRDB table in `bible.sqlite`. Three target scopes, five semantic categories, multi-row per target.

### `bibleAnnotation` table

| Column | Type | Notes |
|---|---|---|
| `id` | TEXT | UUID, primary key |
| `target` | TEXT | `book` \| `chapter` \| `verse` |
| `bookId` | TEXT | 3-letter UPPERCASE book code (e.g. `GEN`, `ROM`, `JHN`, `1PE`) — same form `BibleBookCatalog.standard` uses |
| `chapterNumber` | INTEGER? | set when `target` is `chapter` or `verse` |
| `verseStart` | INTEGER? | set when `target` is `verse`, ≥1 |
| `verseEnd` | INTEGER? | set when `target` is `verse`, ≥ `verseStart` (equals `verseStart` for single-verse) |
| `category` | INTEGER | `BibleAnnotationCategory` raw value: `1` author, `2` summary, `3` historical, `4` clarification, `5` reference. The value *is* the canonical sort order. |
| `title` | TEXT | short heading shown on the card |
| `body` | TEXT | for every category except `reference`: markdown content. For `category=reference`: a citation string parsed by `BibleCitationParser` (e.g. `"Heb 4:15"`). |
| `source` | TEXT | `user` \| `userBulk` |
| `modelId` | TEXT | identifier of the LLM that produced the row (e.g. `afm-3.0`, `claude-sonnet-4-6`). Empty string allowed until the integration PR wires the active session's model id. |
| `createdAt` | DATETIME | timestamp; secondary sort after `category`, with `id` as the final tiebreak for stable order within identical timestamps |

**Indexes:**

- `bibleAnnotation_on_bookId_chapterNumber_verseEnd` — drives the chapter-scoped `@Query` the chapter renderer observes for bubble visibility and per-verse grouping (bubbles render after `verseEnd`).
- `bibleAnnotation_on_target_bookId` — drives book-picker bubble visibility.

**Multi-row semantics.** A book / chapter / verse range can have N annotation rows. Ordering within a target group is `(category ASC, createdAt ASC, id ASC)` — cards sort into their canonical semantic order (author → summary → historical → clarification → reference) regardless of the order the LLM emitted them. Regenerate is a single transaction that deletes all rows for the target group *and* inserts the freshly produced rows; if the LLM call fails before that transaction runs, the existing rows stay untouched (no empty window).

Overlapping verse-annotation ranges that share a `verseEnd` produce multiple bubbles after the same verse — naturally, by query result. The Claude Design canvas confirms this stacks as side-by-side trailing bubbles, each independently tappable.

### Swift surface

```swift
public struct BibleAnnotationRecord: Codable, FetchableRecord, PersistableRecord, Sendable, Equatable, Identifiable {
    public static let databaseTableName = "bibleAnnotation"

    public var id: String
    public var target: BibleAnnotationTarget   // .book, .chapter, .verse
    public var bookId: String
    public var chapterNumber: Int?
    public var verseStart: Int?
    public var verseEnd: Int?
    public var category: BibleAnnotationCategory  // .author … .reference (Int-backed)
    public var title: String
    public var body: String
    public var source: BibleAnnotationSource   // .user, .userBulk
    public var modelId: String
    public var createdAt: Date
}

public enum BibleAnnotationTarget: String, Codable, Sendable, CaseIterable {
    case book, chapter, verse
}

public enum BibleAnnotationCategory: Int, Codable, Sendable, CaseIterable, Comparable {
    case author = 1, summary, historical, clarification, reference
    // Raw values are the canonical display order. `rendering` is derived:
    // .reference → .citation (body is a scripture citation parsed at render
    // time), every other category → .prose (body is markdown).
    public var rendering: BibleAnnotationRendering { self == .reference ? .citation : .prose }
}

public enum BibleAnnotationRendering: Sendable, Equatable { case prose, citation }

public enum BibleAnnotationSource: String, Codable, Sendable, CaseIterable {
    case user        // single-target user-triggered generation
    case userBulk    // bulk runner (future; M-B / M-C)
}
```

### Repository

```swift
public protocol BibleAnnotationRepository: Sendable {
    func list(
        target: BibleAnnotationTarget,
        bookId: String,
        chapterNumber: Int?,
        verseStart: Int?,
        verseEnd: Int?
    ) async throws -> [BibleAnnotationRecord]

    /// Atomically delete-then-insert: replace the target group's rows in one transaction.
    /// Pass an empty `inserting:` array to use this as a pure delete.
    func replace(
        target: BibleAnnotationTarget,
        bookId: String,
        chapterNumber: Int?,
        verseStart: Int?,
        verseEnd: Int?,
        inserting records: [BibleAnnotationRecord]
    ) async throws

    func deleteOne(id: String) async throws
}
```

Concrete impl: `GRDBBibleAnnotationRepository` over `BibleDatabase`.

### Reactive bubble visibility

The chapter renderer (`BibleChapterReader`) already owns a highlight `@Query` per the Bible AGENTS. Annotations layer the same pattern: a new `ChapterAnnotationsRequest: ValueObservationQueryable` returns `[BibleAnnotationRecord]` for the on-screen chapter. The chapter renderer groups rows by `verseEnd` to position bubbles. The book picker observes `BookAnnotationsExistenceRequest` returning `Set<String>` of `bookId`s that have ≥1 row at `target = .book`.

Per the Bible AGENTS rule: decorations (highlights, saved verses, reading-plan progress, **annotations**) bind reactively because they get written from outside the chapter renderer.

## 4. The `bible.annotate` tool

One tool, registered with the Core `ToolRegistry` from each composition root (`SuperBibleAppBootstrap` / `SuperOSAppBootstrap`), mirroring the `TimeNowTool` and `MemoryTool` pattern. `BibleApplet` exposes a public `registerAnnotationTool(in:)` helper the bootstraps call after constructing the applet, so the Bible-internal database stays inside the applet.

### Tool descriptor (LLM-facing)

```
id:           bible.annotate
appletId:     bible
name:         bible.annotate
category:     .mutation
description:  (see prompt language below)
parameters:
  - target:        "book" | "chapter" | "verse"   (required)
  - bookId:        string                          (required, 3-letter uppercase code)
  - chapterNumber: integer                         (required for chapter & verse targets)
  - verseStart:    integer                         (required for verse target)
  - verseEnd:      integer                         (required for verse target, ≥ verseStart)
  - entries:       array of objects                (required, ≥1)
      - category: "author" | "summary" | "historical" | "clarification" | "reference"
      - title:    string
      - body:     string
```

**Prompt language** (the descriptor's `description` field — embedded verbatim in the tool):

> Produce one or more annotation cards for the requested target. Each card is a short, focused note classified by `category`. Keep each body to ~240 characters / ≤2 sentences unless the user explicitly asks for more depth — readers see these in a tight popover.
>
> Each entry's `category` is one of `author`, `summary`, `historical`, `clarification`, `reference`. The category sets both the card's display order (author → summary → historical → clarification → reference) and its rendering: `reference` bodies are a single citation like `"Heb 4:15"` or `"Romans 8:28-30"`; every other category's body is markdown. Use clear, plain-language titles (e.g. `"Author"`, `"Historical context"`, `"See also"`).

### Execution

`AnnotateBibleTool: ToolExecutor` (in `Packages/Bible/Sources/Bible/Tools/AnnotateBibleTool.swift`):

1. Validate input shape per the descriptor.
2. Resolve `source` + `modelId` from an injected `BibleAnnotationStampProvider`: per-target tap and in-chat use stamp `.user`; future bulk runner stamps `.userBulk`. ModelId comes from the same provider — wired to the active LLM session in PR3 integration; empty string until then.
3. Generate `id` (via injected `IDGenerator`) and `createdAt` (via injected `Clock`) per entry.
4. Insert all entries via `BibleAnnotationRepository.replace(...)` — atomic delete+insert for the target group, so regenerate never leaves a partial state.
5. Return `ToolResult` with content listing inserted IDs and `artifacts` carrying one `Artifact(type: "annotation", id: ...)` per inserted row.

### Three callers (all dispatch through the same tool)

1. **Per-target tap** — the bubble-tap and verse-annotate UI flows call Chat's tool dispatcher headlessly (no chat turn).
2. **In-chat use** — the user says "annotate Romans 8" in a chat conversation; the tool routes naturally as part of a turn; next time the user opens that chapter, the bubble is filled.
3. **Bulk runner** — future. Background-task driver invokes the tool in a loop with `.userBulk` source tag.

## 5. UI affordances

The bubble glyph (pill speech-bubble, see Claude Design's `super/project/annotations/atoms.jsx` `AnnotationBubble`) is the universal entry point. Three states:

| State | Cue | Tap behavior |
|---|---|---|
| **Empty** | Outlined / ghosted (1.6 stroke in `inkFaint`) | Fires `bible.annotate` immediately (no confirmation sheet — one fewer tap on a free local model). Bubble swaps to *Generating*. |
| **Generating** | Three static dots inside the bubble outline | Disabled |
| **Filled** | Solid silhouette in `accent` color | Opens the `AnnotationSheet` popover with cards |

**Where bubbles appear:**

| Surface | Empty bubble shown? | Notes |
|---|---|---|
| Book picker (66 rows) | Yes | One per book |
| Chapter title (1,189 chapters) | Yes | One per chapter |
| Verse ranges in the reader | **No empty bubbles** | Bubbles only appear at `verseEnd` of ranges that have ≥1 annotation row. Entry for un-annotated verses is via (a) the chapter nav's **spark button** when verses are selected, or (b) the **"Annotate"** tile in the existing verse action modal. |

Showing empty bubbles next to every verse would paint 31,103 ghost bubbles per Bible — visual noise. Verses are entered explicitly via selection-driven actions, not passive affordances.

**Non-contiguous selections:** if the user selects verses 28-30 plus 32, two tool calls fire — one per contiguous range. Two bubbles appear (after v30 and after v32). The repository's uniqueness is `(target, bookId, chapterNumber, verseStart, verseEnd)` per row.

### `AnnotationSheet` popover

- iOS sheet (`presentationDetents`, medium → drag to large).
- Drag handle, header with citation (e.g. "Romans 8:28-30") + uppercase mono "Annotations" label + popover-level kebab menu.
- Body: vertical stack of `AnnotationBlock` rows.
- Each block: a leading **category badge** (an `accentSoft` rounded square holding the category's glyph in `accent` — one shared accent treatment, no per-category color), the uppercase mono title, body rendered per `category.rendering`, footer line with provenance (`Generated by {modelId} · {humanDate}`), per-block overflow menu (`Add to chat`, `Delete this card`).
- Popover-level kebab menu actions: **"Regenerate"** (fires `bible.annotate` for the same target; `replace(...)` swaps old rows for new in one transaction) and **"Add all to chat"** (publishes a single `RecordReference` carrying the whole popover content).

### Spark button

A pill-shaped 36×36 button in the chapter nav bar (top-right). Glyph: sparkle (chosen by Claude Design to read as "AI generate" without resembling Apple Intelligence trademarks). States:

- **Dim / disabled** when no verses are selected — `bgRaised` background, `borderFaint` outline, `inkMute` glyph.
- **Active** when verses are selected — `accent` background, `accentInk` glyph, light glow shadow. Tap fires `bible.annotate` for each contiguous range in the selection.

### Views (per Bible AGENTS naming — drop `View` suffix, bucket suffix per role)

- `AnnotationBubble` — the glyph; pure stateless render of state + tap callback.
- `AnnotationSheet` — the popover (`.sheet` with `presentationDetents`).
- `AnnotationBlock` — one card row inside the sheet. (`Block` is the bucket per `docs/NAMING_CONVENTIONS.md` Part 4.)
- `AnnotationDisclaimerSheet` — the one-time first-run warning.
- `SparkButton` — the chapter-nav annotate-selection trigger.

Visual reference: the Claude Design canvas mockups in `super/project/annotations/{atoms,sheet,screens,mockups}.jsx`. SwiftUI views match the JSX visually (theme tokens map onto SuperTheme; glyph SVG paths translate to SwiftUI `Path` shapes).

## 6. Chat injection

Annotations reuse the existing `.recordAddedToChat` SuperEvent (Bible already publishes it for verse selections — see `BibleScreen.publishReferenceToChat`). No Core type changes; no Chat-side consumer changes.

`RecordReference` is a flat struct (`appletID`, `kind`, `sourceID`, `id`, `displayLabel`, `citation`, `snapshot` — see `Packages/Core/Sources/Core/Events/RecordReference.swift`). The receiver treats every field as opaque, so new `kind` values flow through `ChatReferenceInbox` unchanged.

**Single-card "Add to chat":**

```swift
let ref = RecordReference(
    appletID: "bible",
    kind: "annotation",
    sourceID: annotation.id,                                       // single row
    displayLabel: "<citation> annotation",                          // e.g. "Romans 8:28-30 annotation"
    citation: "<citation>",
    snapshot: AnnotationSnapshotComposer.compose(annotation: annotation)
)
eventBus.publish(.recordAddedToChat(reference: ref, startNewConversation: false))
```

**Popover-level "Add all to chat":**

```swift
let ref = RecordReference(
    appletID: "bible",
    kind: "annotationGroup",
    sourceID: annotations.map(\.id).joined(separator: ","),
    displayLabel: "<citation> annotations (N)",
    citation: "<citation>",
    snapshot: AnnotationSnapshotComposer.compose(annotations: annotations)
)
```

`AnnotationSnapshotComposer` is a pure, testable formatter that renders annotations into the markdown block the LLM receives. Reference-category cards render as resolved citations (e.g. `John 1:14`) so the LLM sees a clean text representation, not a deep-link URL.

## 7. Verse navigation from reference cards

`category: .reference` cards render the `body` as a tappable button labeled with the parsed citation (e.g. "John 1:14"). Tapping navigates the Bible reader to that verse range.

This is **intra-applet navigation only.** The annotation popover lives inside the Bible applet, so the tap handler calls directly into the Bible view model's existing position-change seam (the same seam chapter swipes and the chapter picker already use). No `SuperEventBus` publish, no `super://` URL, no cross-applet routing.

> **Out of scope:** chat-side verse deep linking (Chat → Bible navigation when the user taps a scripture reference inside a chat message). That work *does* need cross-applet routing and lands in a separate effort.

### `BibleCitationParser`

New file: `Packages/Bible/Sources/Bible/Formatting/BibleCitationParser.swift`. Sibling of `BibleCitationFormatter`, parse-direction. Public surface:

```swift
public enum BibleCitationParser {
    /// Best-effort parse of a citation string into a position + verse range.
    /// Returns nil if the string can't be resolved to a real book.
    public static func parse(
        _ input: String,
        in catalog: BibleBookCatalog
    ) -> ParsedCitation?

    public struct ParsedCitation: Sendable, Equatable {
        public let position: BiblePosition
        public let verseStart: Int
        public let verseEnd: Int  // equals verseStart for single-verse citations
    }
}
```

Accepted forms:

- `"John 3:16"` → single verse
- `"John 3:16-17"` → range
- `"1 Corinthians 13:4-7"` → multi-word book + range
- `"1Cor 13:4"`, `"1 Cor 13:4"`, `"1 cor 13:4"` — case-insensitive abbreviation lookup
- `"Heb 4:15"` → 3-letter abbreviation matched against `BibleBookCatalog.standard` book ids

Fallback: if parse returns nil, the card body renders as plain text (no tappable button). The user still sees the content; just no tap-to-jump.

### Navigation flow

On tap of a parsed reference card:

1. Dismiss the popover (sheet dismiss animation).
2. The parsed `BiblePosition` + verse range is handed to Bible's view-model navigation entry point (the same one that drives chapter swipes / the chapter picker — exact symbol pinned during PR3 integration, see `Packages/Bible/Sources/Bible/UI/BibleScreen.swift` for current navigation entry points).
3. If the target book or chapter differs from what's on screen, the reader loads it; the reader scrolls to and visually highlights the target verse range using the existing chapter-load → scroll-to-position flow.

## 8. Liability framing & disclaimers

Three placements:

1. **First-run disclaimer (`AnnotationDisclaimerSheet`)** — shown the first time the user fires any annotation tool call. Body:
   > Annotations are AI-generated and may contain errors. SuperBible doesn't verify theological accuracy.
   >
   > Treat them as a starting point — not as commentary you'd cite.

   Dismissable; persisted via `UserDefaults.standard.set(true, forKey: "bible.annotations.disclaimerAcknowledged")`. Subsequent tool calls skip the sheet.

2. **Per-card provenance** — every block's footer reads `Generated by {modelId} · {humanDate}`. No warning text per card; provenance is the implicit signal.

3. **Settings → About annotations** — longer explanation, model limits, regenerate guidance. Deferred from M-A; the first-run disclaimer alone is sufficient for shipping.

## 10. Testing

Module suite (`swift test` from `Packages/Bible/`) green before any PR, per root AGENTS §Testing.

### Unit

- `BibleAnnotationRecord` round-trips through `BibleDatabase` (in-memory `DatabaseQueue`): insert → list → delete.
- `BibleAnnotationCategory` raw values lock the canonical order; `Comparable` sort and the `rendering` projection (reference→citation, else prose) are covered without the DB.
- The annotation `@Query` requests return rows in `(category, createdAt, id)` order — a regression test inserts rows whose creation order is the reverse of category order and asserts the category sort wins; respects all three target shapes (book / chapter / verse).
- `GRDBBibleAnnotationRepository.replace(...)` is atomic — a thrown error mid-replace leaves prior rows intact.
- `ChapterAnnotationsRequest` `@Query` updates reactively on insert / delete (integration via `GRDBSnapshotTesting` for the database side).
- `BibleCitationParser` parses the documented form list; returns nil for malformed input; round-trip with `BibleCitationFormatter` for clean inputs.
- `AnnotationSnapshotComposer` produces stable, line-deterministic markdown blocks for single and multi-card inputs (snapshot via plain-text fixture).

### Tool

- `AnnotateBibleTool` with strict mock `BibleAnnotationRepository`: scripted tool inputs assert `source` derivation, `modelId` stamping, the parsed `category` on each inserted row, and validation rejects on missing-target-required-fields and unknown/missing `category`.

### Chat injection

- `RecordReference` produced with `kind: "annotation"` flows through a real in-memory `SuperEventBus`; a test-side observer (substituting `ChatReferenceInbox`) receives the reference unchanged.

### UI snapshots (per Bible AGENTS §Tests — PR 2)

Light / dark / sepia × default + Dynamic Type XXL, recorded on the CI Xcode 26.4.1 + iOS 26.4 + iPhone 17 pin:

- `AnnotationBubble`: empty / generating / filled / multi-bubble-stack (3 bubbles after one verse).
- `AnnotationSheet`: 0 / 1 / 3 / 8 cards, plus one-card-per-category (exercises every badge glyph).
- `AnnotationBlock`: prose render (non-reference category) with its badge; `category: .reference` resolved (deep-link button); `category: .reference` parse-failed fallback.
- `AnnotationDisclaimerSheet`.
- `SparkButton`: dim / active.

Coverage target ≥70% per Bible AGENTS.

## 11. Future work

Designed at the data model level, deferred from M-A.

### M-B — bulk for books + chapters

Settings → "Generate annotations" → buttons:

- "Generate all book prologues" — 66 units.
- "Generate all chapter summaries" — 1,189 units.

Foreground long-running task; resumability via new `bulkAnnotationRun` + `bulkAnnotationRunUnit` tables (checkpoints which units are `pending` / `done` / `failed`). Cancellable. Progress sheet. Rows written with `source: .userBulk`. Bubbles fill incrementally as units complete (reactive `@Query` already in place).

### M-C — bulk for notable verses

Adds a third Settings button. Per-chapter call asking the LLM to both identify the most-annotatable verses AND generate annotations for them in one shot (single-call-per-chapter rank-and-generate). ~1,189 chapter-level calls producing several thousand verse-annotation rows.

### Background tasks

`BGProcessingTask` integration to let bulk runs continue when the app is backgrounded. Foreground-only is acceptable for M-B initial; backgrounding lands in M-B+ once usage signal warrants the extra complexity.

### User editing / manual reorder

Adds a `position: Int` column plus a non-LLM write path on the repository for manual edits. Deferred until UX signal warrants it.

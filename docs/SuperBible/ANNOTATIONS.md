# SuperBible — Annotations

> AI-generated study notes attached to books, chapters, and verse ranges. Users generate them on demand from the reader. Notes are stored locally per device, never shared, never pre-bundled.

**Status (2026-06-12):** Shipped, redesigned. M-A (per-target on-demand generation), M-B/M-C (the bulk runner), and the single-summary redesign are all live. The redesign replaced the original multi-card category model (five `(category, title, body)` cards per target) with **one long-form markdown summary per target** — the `v9_annotationSummary` migration rebuilt the table destructively.

## 1. What this is

One long-form AI-generated study summary per target — a single markdown card (~150–400 words, scaled to scope) surfaced behind tappable bubble glyphs in the Bible reader and book picker. The summary is structured with short `###` headings; the sections it covers vary by scope:

- **Book-level**: authorship and date, an overview of the book's argument and major themes, and its historical setting — shown beside the book name in the picker.
- **Chapter-level**: what the chapter says (its argument or narrative), an outline of its movements, and the key context a reader needs — shown beside the chapter title in the reader.
- **Verse-range level**: the passage's meaning in plain language, the historical and literary context, and — only when the passage directly quotes, alludes to, or cites another scripture (e.g. NT drawing on the OT) — genuine cross-references. No cross-reference section for merely thematically similar verses. Shown after the last verse of a contiguous range the user selected.

> These per-scope section lists are mirrored by `BibleAnnotateDispatcher.sectionGuidance(forKind:)` (the prompt steer the headless dispatcher sends per target kind) — **keep the two in sync**. The bulk-only `"chapterVerses"` kind ([§11](#11-bulk-annotations-m-b--m-c)) reuses the verse-range section list, applied to each verse range the model picks.

Scripture citations inside the summary use the full book name (`Romans 8:28-30`, `Psalm 23`); the shared markdown renderer auto-links exactly that format into tappable references that navigate the reader (see [§7](#7-verse-navigation-from-in-summary-citation-links)). The summary never repeats the target's own verse text verbatim — the card quotes the passage itself above the summary for verse-range targets.

All annotations are generated by the user on demand via the user's current Chat LLM (AFM on-device by default; BYOK Claude / Gemini / Ollama / etc. if the user has upgraded). The app ships **no pre-generated content** — every row in the database was produced by an LLM call the user explicitly triggered. SuperBible takes no editorial position on theological accuracy.

## 2. Concepts & terminology

| Term | Meaning |
|---|---|
| **Annotation** | One row in the `bibleAnnotation` table. Represents the *single card* attached to a target — one long-form markdown summary. One row per target is the steady state (generation goes through `replace(...)`). |
| **Target** | What the annotation is attached to: `.book`, `.chapter`, or `.verse`. |
| **Summary** | The card's content: long-form markdown (`###` headings, bold key terms, lists, blockquotes). Citations inside it are auto-linkified by the shared renderer. |
| **Source** | Where the annotation came from: `.user` (the user tapped to generate this one) or `.userBulk` (the bulk runner). Same write path, different tag. |
| **Bubble** | The on-screen glyph indicating an annotation exists (filled) or invites generation (empty). |

The original design's **Category** (`.author` … `.reference`) is gone — the redesign collapsed the five-card taxonomy into the one summary's `###` sections.

## 3. Data model

Single GRDB table in `bible.sqlite`. Three target scopes, one summary row per target.

### `bibleAnnotation` table

| Column | Type | Notes |
|---|---|---|
| `id` | TEXT | UUID, primary key |
| `target` | TEXT | `book` \| `chapter` \| `verse` |
| `bookId` | TEXT | 3-letter UPPERCASE book code (e.g. `GEN`, `ROM`, `JHN`, `1PE`) — same form `BibleBookCatalog.standard` uses |
| `chapterNumber` | INTEGER? | set when `target` is `chapter` or `verse` |
| `verseStart` | INTEGER? | set when `target` is `verse`, ≥1 |
| `verseEnd` | INTEGER? | set when `target` is `verse`, ≥ `verseStart` (equals `verseStart` for single-verse) |
| `summary` | TEXT | long-form markdown study summary — headings, bold, lists, blockquotes, full-book-name scripture citations the renderer auto-links |
| `source` | TEXT | `user` \| `userBulk` |
| `modelId` | TEXT | identifier of the LLM that produced the row (e.g. `afm-3.0`, `claude-sonnet-4-6`). Empty string allowed; renders as "AI" in the provenance footer. |
| `createdAt` | DATETIME | timestamp; primary sort, with `id` as the tiebreak for stable order within identical timestamps |

**Migration:** `v9_annotationSummary` drops and recreates the table — destructive by design, like v5 before it. The old entries model (`category`, `title`, `body` and the category CHECK) has no mapping onto the single-summary model; annotations are cheap, local-only, and regenerated on demand, so we drop and rebuild rather than migrate content. v9 also clears the bulk ledger (`bulkAnnotationRunUnit` then `bulkAnnotationRun` — explicitly ordered, because `DatabaseMigrator` runs with foreign keys off so the v6 cascade doesn't fire inside migrations): a `done` unit asserts "this chapter's annotations exist", which the rebuild just falsified.

**Indexes** (recreated by v9, unchanged in shape):

- `bibleAnnotation_on_bookId_chapterNumber_verseEnd` — drives the chapter-scoped `@Query` the chapter renderer observes for bubble visibility and per-verse grouping (bubbles render after `verseEnd`).
- `bibleAnnotation_on_target_bookId` — drives book-picker bubble visibility.

**One-row-per-target semantics.** Generation always goes through `replace(...)` — an atomic delete-then-insert that clears the target group's prior rows before inserting the fresh one — so one row per target is the intended steady state. There is deliberately **no UNIQUE constraint** on the position tuple (the nullable columns would need COALESCE gymnastics), so readers stay array-shaped and render the *newest* row defensively; a stray duplicate is harmless and converges on the next regenerate or delete. Ordering within a target group is `(createdAt ASC, id ASC)`. If the LLM call fails before the `replace` transaction runs, the existing row stays untouched (no empty window).

Overlapping verse-annotation ranges that share a `verseEnd` produce multiple bubbles after the same verse — naturally, by query result — each independently tappable.

### Swift surface

```swift
public struct BibleAnnotationRecord: Codable, FetchableRecord, PersistableRecord, Sendable, Equatable, Identifiable {
    public static let databaseTableName = "bibleAnnotation"

    public var id: String
    public var target: BibleAnnotationTarget   // .book, .chapter, .verse
    public var bookId: String
    public var chapterNumber: Int?
    public var verseStart: Int?
    public var verseEnd: Int?
    public var summary: String                 // long-form markdown
    public var source: BibleAnnotationSource   // .user, .userBulk
    public var modelId: String
    public var createdAt: Date
}

public enum BibleAnnotationTarget: String, Codable, Sendable, CaseIterable {
    case book, chapter, verse
}

public enum BibleAnnotationSource: String, Codable, Sendable, CaseIterable {
    case user        // single-target user-triggered generation
    case userBulk    // bulk runner (M-B / M-C)
}
```

`BibleAnnotationTargetSpec` (a `book` / `chapter` / `verseRange` enum) is the value the UI passes around to name a target — the sheet's presentation item, the dispatch-status key, and the `@Query` parameter.

### Repository

```swift
public protocol BibleAnnotationRepository: Sendable {
    /// All annotation rows in a target group, in canonical display order
    /// (createdAt ASC, id ASC).
    func list(
        target: BibleAnnotationTarget,
        bookId: String,
        chapterNumber: Int?,
        verseStart: Int?,
        verseEnd: Int?
    ) async throws -> [BibleAnnotationRecord]

    /// Atomically delete-then-insert: replace the target group's rows in one transaction.
    /// Pass an empty `inserting:` array to use this as a pure delete.
    func replace(
        target: BibleAnnotationTarget,
        bookId: String,
        chapterNumber: Int?,
        verseStart: Int?,
        verseEnd: Int?,
        inserting records: [BibleAnnotationRecord]
    ) async throws

    /// `true` when the target slot already has a row — the bulk runner's
    /// preserve mode reads this to skip a unit before generating.
    func hasAnnotation(
        target: BibleAnnotationTarget,
        bookId: String,
        chapterNumber: Int?,
        verseStart: Int?,
        verseEnd: Int?
    ) async throws -> Bool

    func deleteOne(id: String) async throws

    /// Clears every annotation — the hub's "Delete all annotations" reset.
    func deleteAll() async throws
}
```

Concrete impl: `GRDBBibleAnnotationRepository` over `BibleDatabase`.

### Reactive bubble visibility

The chapter renderer (`BibleChapterReader`) already owns a highlight `@Query` per the Bible AGENTS. Annotations layer the same pattern: `ChapterAnnotationsRequest: ValueObservationQueryable` returns `[BibleAnnotationRecord]` for the on-screen chapter, grouped by `verseEnd` to position bubbles. The book picker observes `BookAnnotationsExistenceRequest`. The annotation sheet itself binds through `BibleAnnotationsByTargetRequest` (see [§5](#5-ui-affordances)) — the sheet's container holds a `@Query`, no view model.

Per the Bible AGENTS rule: decorations (highlights, notes, **annotations**) bind reactively because they get written from outside the chapter renderer — the LLM tool, the in-chat orchestrator, the bulk runner, and the sheet's own regenerate path all write rows the queries pick up automatically.

## 4. The `bible.annotate` tool

One tool, registered with the Core `ToolRegistry` from each composition root (`SuperBibleAppBootstrap` / `SuperOSAppBootstrap`) via `AnnotateBibleTool.registration(...)`. The provenance fields (`source`, `modelId`) come from an injected `BibleAnnotationStampProvider` so the bulk path can stamp `.userBulk` without a separate tool.

### Tool descriptor (LLM-facing)

```
id:           bible.annotate
appletId:     bible
name:         bible.annotate
category:     .mutation
description:  (see prompt language below)
parameters:
  - target:        "book" | "chapter" | "verse"   (required)
  - bookId:        string                          (required, 3-letter uppercase code)
  - chapterNumber: integer                         (required for chapter & verse targets)
  - verseStart:    integer                         (required for verse target)
  - verseEnd:      integer                         (required for verse target, ≥ verseStart)
  - summary:       string                          (required, markdown)
```

**Prompt language** (the descriptor's `description` field — see `AnnotateBibleTool.swift` for the authoritative copy):

> Call this ONLY when the user explicitly asks to annotate a passage — to "annotate" or "add study annotations to" a book, chapter, or verse range. It writes one persistent markdown study summary into the Bible reader. When the user just asks you to explain, give context on, or summarize a passage, answer in the conversation instead — do not call this tool (you may offer annotating as a next step). For a free-text personal note or reflection ("save a note", "note that…"), use the `bible.note` tool instead, NOT this one.
>
> Produce ONE markdown study summary of the target passage in `summary`. Long-form: roughly 150–400 words scaled to scope (a verse range shorter, a whole book longer). Structure it with short `###` headings, bold key terms, and bullet lists or blockquotes where they genuinely help. Cover what the passage says in plain language, authorship and historical context, and notable cross-references — but cite a cross-reference ONLY when the target text genuinely quotes, alludes to, or is quoted by that passage; skip merely thematically similar verses. Cite scripture with the full book name in `Book Chapter:Verse` form (e.g. `Romans 8:28-30`, `Psalm 23`) — the reader auto-links exactly that format into tappable references. Do NOT repeat the target's own verse text verbatim; the reader displays it above the summary.
>
> Calling this tool replaces any existing annotation for the same target. Call it at most once per target.

### Execution

`AnnotateBibleTool: ToolExecutor` (in `Packages/Bible/Sources/Bible/Tools/AnnotateBibleTool.swift`):

1. Validate input shape per the descriptor. Validation rejects *softly* — a bad payload returns `ToolResult(isError: true)` with a remediation message instead of throwing, so the LLM sees the failure and can retry rather than tearing down the turn.
2. Resolve `source` + `modelId` from the injected `BibleAnnotationStampProvider`: per-target tap and in-chat use stamp `.user`; the bulk runner stamps `.userBulk`.
3. Generate `id` (via injected `IDGenerator`) and `createdAt` (via injected `Clock`).
4. Write the single record via `BibleAnnotationRepository.replace(...)` — atomic delete+insert for the target group, so a re-annotate converges on the one-row-per-target steady state and never leaves a partial state.
5. Return `ToolResult` with one `Artifact(type: "annotation", id: ...)` for the inserted row.

### Three callers (all dispatch through the same tool)

1. **Per-target tap** — the bubble-tap, sparkles-menu, and verse-annotate UI flows publish `SuperEvent.bibleAnnotateRequested(reference:)` on the bus. Chat's **`BibleAnnotateDispatcher`** (shell-owned, attached at bootstrap) drains those envelopes headlessly: each dispatch creates a *transient* `ConversationRecord` (filtered out of the Chats list), runs one `ChatSession.send(...)` turn against a one-tool registry exposing only `bible.annotate`, hard-deletes the transient row when the turn terminates, and publishes `SuperEvent.bibleAnnotateCompleted(requestId:result:)`. The dispatcher replaces the chat persona with `dispatcherBriefing` (call the tool exactly once, no conversational reply) and appends `sectionGuidance(forKind:)` — the per-scope `###` section steer mirroring [§1](#1-what-this-is). For chapter and verse-range targets the request reference's `snapshot` carries the **exact verse text** of the target so the model grounds the summary in the actual translation (a whole-book target carries no snapshot — too large).
2. **In-chat use** — the user says "annotate Romans 8" in a chat conversation; the tool routes naturally as part of a turn; next time the user opens that chapter, the bubble is filled.
3. **Bulk runner** — `BulkAnnotationRunner` drives the same generation seam in a loop with `.userBulk` source tag (see [§11](#11-bulk-annotations-m-b--m-c)).

## 5. UI affordances

The bubble glyph (pill speech-bubble, hand-drawn `Path` — see `AnnotationBubble`) is the universal entry point. Three states:

| State | Cue | Tap behavior |
|---|---|---|
| **Empty** | Outlined / ghosted (1.6 stroke in `inkFaint`) | Fires a `bible.annotate` dispatch immediately (no confirmation sheet — one fewer tap on a free local model). Bubble swaps to *Generating*. |
| **Generating** | Three static dots inside the bubble outline | Disabled |
| **Filled** | Solid silhouette in `accent` color | Opens the `AnnotationSheet` with the card |

**Where bubbles appear:**

| Surface | Empty bubble shown? | Notes |
|---|---|---|
| Book picker (66 rows) | Yes | One per book |
| Chapter title (1,189 chapters) | Yes | One per chapter |
| Verse ranges in the reader | **No empty bubbles** | Filled bubbles render in the `VerseTrailers` cluster (annotation bubble first, note glyph second) after `verseEnd` of ranges that have a row. Entry for un-annotated verses is via (a) the nav bar's **sparkles menu** `Annotate` action when verses are selected, or (b) the **"Annotate"** tile in the verse action sheet. |

Showing empty bubbles next to every verse would paint 31,103 ghost bubbles per Bible — visual noise. Verses are entered explicitly via selection-driven actions, not passive affordances.

**Non-contiguous selections:** if the user selects verses 28-30 plus 32, two dispatches fire — one per contiguous range. Two bubbles appear (after v30 and after v32).

### `AnnotationSheet`

Native sheet via `.sheetPresentation(.expandable)` (same `.medium`/`.large` detents as the book picker). Anatomy, top to bottom:

- **Nav bar** (`SheetNavBar`): the scripture citation as the title (e.g. "Romans 8:28-30"), a small uppercase **ANNOTATION** subtitle, the leading glass close button, and a trailing kebab overflow menu.
- **Kebab actions**: **Regenerate** (always present; re-fires the dispatch for the same target — `replace(...)` swaps the old row for the new in one transaction), and — only when a card exists — **Add to chat** and a destructive **Delete** gated behind a confirmation dialog (per HIG, non-reversible destructive actions in menus confirm).
- **Body**: a vertical scroll hosting the single `AnnotationBlock`, or one of three card-less states: **empty** ("No annotation yet. Tap to generate."), **generating** (spinner bubble; shown while a dispatch is in flight — a regenerate hides the stale card behind the spinner until the fresh row lands), and **error** (the dispatcher's short failure reason + a "Try again" button). A regenerate failure with a card still on screen keeps the previous card — it was never deleted — and silently clears the stale status instead of flipping to the error layout.

The sheet is stateless beyond the local delete-confirmation gate. **`AnnotationSheetContainer`** wraps it with the live `@Query` (`BibleAnnotationsByTargetRequest`) and the mutation seams — no `@Observable` view model, per the Bible AGENTS reactive-decorations rule. The container projects the newest record into the single card (defensively — see [§3](#3-data-model)), composes the provenance line, and routes Delete through `replace(target:..., inserting: [])` — the repository's atomic whole-target clear, so a failure leaves either everything or nothing. Per-target dispatch status (`running` / `failed`) is owned by `BibleScreenViewModel` so the disclaimer gate and toast queue can sequence with it.

### `AnnotationBlock` — the one card

Anatomy, top to bottom:

- **Title**: the scripture citation (`"Romans 8:28–30"`, `"Romans 8"`, `"Romans"`) in the EB Garamond reading face's SemiBold member at 22pt (`typography.reading(22, relativeTo: .title2, weight: .semibold)`).
- **Verse text** (verse-range targets only): the passage itself, rendered with the exact reader recipe — `@ScaledMetric` body size over `typography.reading` plus `BibleReadingMetrics.lineSpacing` — behind a thin leading rule (a blockquote affordance separating scripture from commentary). The text is passed in by `BibleScreen` as a plain `String?` from `BibleScreenViewModel.annotationVerseText(for:)`: the user's **current translation**, verses joined without verse numbers; `nil` for chapter/book targets (a whole chapter is too long to inline) and when the text fails to load — the card degrades to title + summary.
- **Summary**: the record's long-form markdown through Core's shared **`MarkdownText`** renderer — the same engine as Chat's assistant messages, so annotation prose paints with the same faces, palette, and block chrome. The sheet applies the `bibleMarkdownRendering(openLink:)` modifier (UI/BibleMarkdownRendering.swift), which projects the global font-scale slider onto `\.markdownBodyMetrics` and routes citation-link taps — apply it at the root of any future Bible surface that hosts `MarkdownText`. Scripture citations inside the summary are auto-linkified (see [§7](#7-verse-navigation-from-in-summary-citation-links)).
- **Footer**: a small mute-ink provenance line, `Generated by {modelId} · {humanDate}` (empty `modelId` renders as "Generated by AI · …").

The block is stateless and carries no actions — Regenerate / Add to chat / Delete live in the sheet's nav-bar kebab, since the sheet hosts exactly one card.

### Sparkles menu

The chapter nav bar's trailing control is a sparkles `Menu` (`BibleNavBar.SparkMenuAction`): **Annotate**, **Add to chat**, **New chat**, **Narrate**. The first three are selection-aware — they act on the selected verses when any are selected, else on the whole chapter. (This replaced the original standalone spark button.)

### Views (per Bible AGENTS naming — drop `View` suffix, bucket suffix per role)

- `AnnotationBubble` — the glyph; pure stateless render of state + tap callback.
- `AnnotationSheet` — the stateless sheet (nav bar + single card / empty / generating / error states).
- `AnnotationSheetContainer` — the `@Query`-bound Region wrapping the sheet with live data and mutation seams.
- `AnnotationBlock` — the one card. (`Block` is the bucket per `docs/NAMING_CONVENTIONS.md` Part 4.)
- `AnnotationDisclaimerSheet` — the one-time first-run warning.
- `VerseTrailers` — the inline decoration cluster (annotation bubble + note glyph) trailing a verse.

## 6. Chat injection

Annotations reuse the existing `.recordAddedToChat` SuperEvent (Bible already publishes it for verse selections — see `BibleScreen.publishReferenceToChat`). No Core type changes; no Chat-side consumer changes.

`RecordReference` is a flat struct (`appletID`, `kind`, `sourceID`, `id`, `displayLabel`, `citation`, `snapshot` — see `Packages/Core/Sources/Core/Events/RecordReference.swift`). The receiver treats every field as opaque, so new `kind` values flow through `ChatReferenceInbox` unchanged.

**"Add to chat"** (the sheet kebab; the only chat-injection affordance — the multi-card "Add all to chat" went away with the multi-card model):

```swift
let ref = RecordReference(
    appletID: "bible",
    kind: "annotation",
    sourceID: record.id,                                            // the single row
    displayLabel: "<citation> annotation",                          // e.g. "Romans 8:28-30 annotation"
    citation: "<citation>",
    snapshot: AnnotationSnapshotComposer.compose(annotation: record, citation: citation)
)
eventBus.publish(.recordAddedToChat(reference: ref, startNewConversation: false))
```

`AnnotationSnapshotComposer` is a pure, testable formatter that renders the annotation into the markdown block the LLM receives:

```
## {citation} — annotation

{summary}
```

The summary is already markdown and is passed through as-is; its citations stay plain text here — the tappable-link rendering is purely a UI affordance inside the sheet and has no place in the chat context.

## 7. Verse navigation from in-summary citation links

Scripture citations *inside* the rendered summary are tappable. (This replaced the original design's dedicated reference cards — cross-references are now just citations in the summary's prose, like any other.)

The pipeline:

1. **Linkify** — Core's `BibleReferenceLinkifier` (part of the shared `MarkdownText` render path) scans the markdown for full-book-name citations in `Book Chapter:Verse` form (`Romans 8:28-30`, `Psalm 23`, same-sentence continuations like `Romans 8:1; 12:1-2`) and wraps each in a `super://bible/verse?book=…&chapter=…&verses=…` markdown link. Chapter numbers are validated against the book's chapter count; code spans and existing links are skipped. This is the same linkification Chat's assistant messages get — the annotation card inherits it for free by rendering through `MarkdownText`.
2. **Intercept** — `AnnotationSheet` installs an `OpenURLAction` on its scroll content: a tapped URL that parses as a `BibleDeepLink(url:)` routes to the sheet's `onOpenLink` callback; non-Bible URLs (a model emitting a real https link) fall through to the system and open in Safari.
3. **Navigate** — `BibleScreen` forwards the link to `BibleScreenViewModel.navigateToDeepLink(_:)`, which dismisses the annotation sheet and routes through the existing `openReference(...)` path — so the chapter swap, the pre-selection, and the scroll-to-verse anchor all behave identically to an external deep link. Chapter-only links (`Psalm 23`) carry nil verses and open the chapter unselected.

This is **intra-applet navigation** — the sheet lives inside the Bible applet and the tap lands on the Bible view model directly; the `super://` URL is just the carrier format the shared renderer emits. (The link's grammar is shared with Chat-side deep linking — a citation tapped in a chat message routes cross-applet through `BibleDeepLinkRouting` and the event bus — but that path is Chat's, not this sheet's.)

`BibleCitationParser` was deleted with the reference-card model — linkification happens in Core at render time (`BibleReferenceLinkifier`), and parsing back is `Core.BibleDeepLink(url:)`.

## 8. Liability framing & disclaimers

Three placements:

1. **First-run disclaimer (`AnnotationDisclaimerSheet`)** — shown the first time the user fires any annotation tool call. Body:
   > Annotations are AI-generated and may contain errors. SuperBible doesn't verify theological accuracy.
   >
   > Treat them as a starting point — not as commentary you'd cite.

   Dismissable; persisted via `UserDefaults.standard.set(true, forKey: "bible.annotations.disclaimerAcknowledged")` (owned by `AnnotationDisclaimerStore`). Subsequent tool calls skip the sheet.

2. **Card provenance** — the card's footer reads `Generated by {modelId} · {humanDate}`. No warning text on the card; provenance is the implicit signal.

3. **Settings → About annotations** — longer explanation, model limits, regenerate guidance. Deferred from M-A; the first-run disclaimer alone is sufficient for shipping.

## 10. Testing

Module suite (`swift test` from `Packages/Bible/`) green before any PR, per root AGENTS §Testing.

### Unit

- `BibleAnnotationRecord` round-trips through `BibleDatabase` (in-memory `DatabaseQueue`): insert → list → delete; the `v9` schema shape is locked with `GRDBSnapshotTesting`.
- The annotation `@Query` requests return rows in `(createdAt, id)` order across all three target shapes (book / chapter / verse).
- `GRDBBibleAnnotationRepository.replace(...)` is atomic — a thrown error mid-replace leaves the prior row intact — and converges duplicates to one row.
- `ChapterAnnotationsRequest` / `BibleAnnotationsByTargetRequest` update reactively on insert / delete.
- `AnnotationSnapshotComposer` produces the stable `## {citation} — annotation` block.

### Tool

- `AnnotateBibleTool` with strict mock `BibleAnnotationRepository`: scripted tool inputs assert `source` derivation, `modelId` stamping, and soft-rejection (`isError: true` + remediation message) on missing/invalid `target` position fields and empty `summary`.

## 11. Bulk annotations (M-B / M-C)

**Status:** Shipped — UI (#192), ledger (#195), generator seam (#201), engine (#210), lifecycle (#213), BGProcessingTask backgrounding (#215), bug-fixes (#226). The single-summary redesign left the runner **structurally unchanged**; only the per-unit yield changed (see below). **M-C (notable verses) shipped** as an opt-in toggle on top of that runner — a `chapterVerses` unit per chapter driving a multi-call rank-and-generate dispatch (see below). Design source lives in `docs/SuperBible/design/bulk/` (`BulkAnnotations.html` + `atoms/screens/mockups.jsx`).

### Shape

One home: **Settings → Annotations**. The hub shows an honest **books · chapters · verses** coverage synopsis (`AnnotationCoverageCard`, backed by `AnnotationCoverageRequest`), then either a **Generate** CTA or the single active **job card** (titled by all books, counted in *annotations*), and a full-width red **Delete all annotations** (→ `repository.deleteAll()`). **Generate sheet:** a flat book list where each book expands to chapters, already-annotated books/chapters carry a **"Done"** badge, and a pinned footer shows a live estimate beside Generate (a one-tap cost confirm precedes the run for remote BYOK models; the free on-device model starts directly). **Per-book progress:** a ring header + pause/cancel over a chapter list (`queued / generating / done / skipped / failed`); **failures isolate per chapter → Retry, never restart**. There is **one job at a time**.

What "generate" produces, by selection granularity: a whole-book selection enqueues one **book-prologue unit** (a `.book`-target annotation) plus one unit per chapter; a chapter selection enqueues just its chapter units. A chapter/book unit yields exactly one annotation — `BulkRunEstimate.annotationsPerChapter = 1`, `producedCount` on such a finished unit is 1. `BulkChapterRow`'s done cell accordingly shows a small **filled annotation bubble** rather than a count ("1" on every row would be noise; VoiceOver reads "annotated").

**Notable verses (M-C — opt-in).** The Generate sheet carries an "Also annotate notable verses" toggle (**off by default**). When on, each chapter additionally enqueues a **`chapterVerses` unit** right after its chapter-summary unit (`BulkRunUnitKind.chapterVerses`, same `chapterNumber`). That unit runs one rank-and-generate dispatch turn keyed by a distinct `reference.kind == "chapterVerses"`: the dispatcher swaps in `BibleAnnotateDispatcher.notableVersesBriefing`, which asks the model to pick **up to 5** of the chapter's most significant verse ranges and call `bible.annotate` once per range (`target: "verse"`). The dispatcher already accumulates the artifact count across every call in the turn, so a `chapterVerses` unit's `producedCount` is however many verses were annotated (0–5+). The 5-cap is a soft prompt instruction — the footer estimate adds `BulkRunEstimate.notableVersesPerChapter = 5` per chapter when the toggle is on. `chapterVerses` units are intentionally absent from the per-book progress grid (like book-prologue units — `BulkChapterProgress` carries only a chapter number); they still generate, persist, and count toward run completion, and their output surfaces as filled verse bubbles in the reader and a rising "verses" coverage count.

"Done"-badge selection *is* the implicit fill-gaps/regenerate (no global mode toggle); preserve mode skips already-annotated slots via `repository.hasAnnotation(...)` without an LLM call — and a `chapterVerses` unit (whose ranges aren't known until generation) is skipped via `repository.hasVerseAnnotations(bookId:chapterNumber:)` once the chapter carries any verse annotation. Rows are stamped `source: .userBulk`; bubbles fill reactively as units complete.

### Backend

`BulkAnnotationRunner` drives the same generation seam as the per-target dispatch path; per-run `bulkAnnotationRun` + `bulkAnnotationRunUnit` ledger tables (with `attemptCount` and `producedCount`) for resume/retry/progress; three-tier retry (per-unit auto-retry + run-level circuit breaker + manual per-chapter retry); atomic `replace` makes retries idempotent; runs keep draining on a `BGProcessingTask` while the app is suspended and resume on launch. The notable-verses opt-in rides the same machinery: a `chapterVerses` unit is an ordinary ledger unit (retry, resume, background drain all work unchanged); only its `RecordReference.kind` and the dispatcher briefing differ, and a single dispatch turn fans out into several `bible.annotate` verse calls that the dispatcher tallies into the unit's `producedCount`.
